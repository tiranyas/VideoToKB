<task type="auto">
  <name>Task 1: Install Playwright and create configuration</name>
  <files>playwright.config.ts, vitest.config.ts, package.json</files>
  <action>
    1. Install dev dependencies:
       ```bash
       npm install -D @playwright/test @vitest/coverage-v8
       npx playwright install chromium
       ```

    2. Create `playwright.config.ts` at project root following the Next.js official pattern from 11-RESEARCH.md:
       - `testDir: './e2e'`
       - `fullyParallel: true`
       - `forbidOnly: !!process.env.CI`
       - `retries: process.env.CI ? 2 : 0`
       - `workers: process.env.CI ? 1 : undefined`
       - `reporter: 'html'`
       - `use.baseURL: 'http://localhost:3000'`
       - `use.trace: 'on-first-retry'`
       - Single project: chromium only (Desktop Chrome device)
       - `webServer.command: 'npm run dev'`
       - `webServer.url: 'http://localhost:3000'`
       - `webServer.reuseExistingServer: !process.env.CI`

    3. Update `vitest.config.ts` to add v8 coverage configuration:
       - Add `coverage.provider: 'v8'`
       - Add `coverage.include: ['src/lib/**/*.ts', 'src/app/api/**/*.ts']`
       - Add `coverage.exclude: ['src/lib/__tests__/**', 'src/**/*.d.ts']`
       - Add `coverage.reporter: ['text', 'html', 'json']`

    4. Add npm scripts to package.json:
       - `"test:e2e": "npx playwright test"`
       - `"test:coverage": "npx vitest run --coverage"`

    5. Create `e2e/` directory and `e2e/helpers/` subdirectory.

    6. Add to `.gitignore` if not already present:
       - `playwright-report/`
       - `test-results/`
       - `coverage/`
  </action>

<task type="auto">
  <name>Task 2: Auth helper and E2E tests for login + articles</name>
  <files>e2e/helpers/auth.ts, e2e/login.spec.ts, e2e/articles.spec.ts</files>
  <action>
    1. Create `e2e/helpers/auth.ts` with a function to inject Supabase auth cookies for E2E tests. Since Supabase uses `sb-{ref}-auth-token` cookies, the helper should:
       - Accept a `BrowserContext` from Playwright
       - Use Supabase admin API (via env vars `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`) to create a test user session
       - Set the auth cookie on the browser context using `context.addCookies()`
       - If admin API approach is too complex, fall back to a simpler approach: create a `storageState.json` file during global setup with valid cookies, and reference it in test config
       - Export `loginAsTestUser(context: BrowserContext): Promise<void>`
       - Add a comment noting this requires `SUPABASE_SERVICE_ROLE_KEY` to be available in the test environment

    2. Create `e2e/login.spec.ts` with tests (NO auth needed):
       ```typescript
       test('unauthenticated user visiting / is redirected to /login', async ({ page }) => {
         await page.goto('/');
         await expect(page).toHaveURL(/\/login/);
       });

       test('login page shows email input', async ({ page }) => {
         await page.goto('/login');
         await expect(page.getByRole('textbox', { name: /email/i })).toBeVisible();
       });

       test('login page shows submit/sign-in button', async ({ page }) => {
         await page.goto('/login');
         // Look for a submit button by role
         await expect(page.getByRole('button', { name: /sign in|log in|send/i })).toBeVisible();
       });
       ```

    3. Create `e2e/articles.spec.ts` with tests that use route interception instead of real auth (avoids Supabase dependency for initial E2E):
       ```typescript
       test('articles page shows article list or empty state', async ({ page }) => {
         // Intercept the middleware auth check — mock the Supabase session cookie
         // For now, verify the page loads at all (may redirect to login)
         // This test documents the expected behavior for when auth is wired up
         await page.goto('/articles');
         // Either shows articles or redirects to login
         const url = page.url();
         expect(url).toMatch(/\/(articles|login)/);
       });
       ```

    Note: The auth helper is foundational infrastructure. Full authenticated E2E flows will be added in a future phase once the auth cookie injection strategy is validated. The login redirect and login page rendering tests are the highest-value E2E tests because they require zero auth setup and verify the most common user journey entry point.
